ERP Suite 3.0: Rebuilding a Legacy ERP for Scale

From a fragile MVP built for 150 products to a scalable platform supporting 15,000+ — through object-oriented components, bulk-first workflows and a system of reusable primitives.

The challenge

Built for 150 products. Forced to support 7,000+.

ERP 2.0 was originally built as an MVP using an Adobe website builder with heavy customisation. As the business scaled past 7,000 products, the system became slow, fragile, and operationally expensive.

The software frequently broke, UX was inconsistent, and every change required significant admin effort. With no designers involved from the start, the system could no longer support business growth. The challenge was to reimagine the ERP from scratch — not as a patch, but as a scalable product platform.

Rewriting. Refactoring. Redesigning.

Discovery

Legacy audit, heuristic evaluation, shadowing admin workflows.

The real bottleneck wasn't feature complexity. It was repetitive admin effort caused by poor system primitives — admins were forced to repeat the same actions hundreds of times across product variants.

Key innovation

Quick Edit

Products move through 6 lifecycle stages and carry 200+ attributes, often with 100+ variants. Earlier, each variant had to be edited individually. Quick Edit lets admins edit an attribute across every variant at once, or selectively override individual variants — without leaving the current screen.

Constraints & reflection

Rebuilt incrementally, module by module.

The business kept operating on ERP 2.0 throughout, so the rebuild had to happen incrementally — requiring careful prioritisation and backwards compatibility during rollout.

What worked
Designing the ERP as a platform of primitives, not a collection of screens.
What I'd do differently
Introduce automation and rule-based defaults earlier to reduce manual decisions further.

Design system

One base component. Every variant built from it.

Every input, select and attachment pattern in ERP Suite 3.0 was built as a variant of the same base component — not as a one-off screen. That kept the product consistent as new modules were added.

Design principles
One base component
Label, input, hint and mandatory state defined once, reused everywhere.
Variants, not rebuilds
Single select, multi-value, unit selectors and attachments — all built from the same foundation.
Consistent by default
New modules inherited the pattern automatically, instead of reinventing it.
Every variant, from one foundation

Single select, multi-value, unit selectors and attachment patterns all trace back to the same base component — not separate screens built one at a time.
