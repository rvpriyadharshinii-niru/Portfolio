Who this is for

Two people share this experience, at two different altitudes.

Designing for both meant giving each the right scope — not the same screen with fewer options switched off.

Platform Admin
Manages the platform.

Owns identity, security and tenant-wide governance. Connects SSO and designates who administers each application.

App Admin
Runs an application.

Designated by the Platform Admin. Configures how one application uses what's already approved and enabled.

Credits & usage

Making AI consumption visible

AI introduces a new administrative concern: consumption. Total inferences and daily burn answer “is this normal?” first — usage by skill and model are one level down.

Both altitudes, different scope. Platform Admin sees the full account bill across every app; App Admin sees only this app's consumption.

Observability

From configuration to operational awareness

Audit Logs, Sign-ins, System Events and Health look similar at first glance, but answer four different administrator questions.

Observability
Audit Logs
“What changed, and who did it?”
Sign-ins
“Who is accessing the platform?”
System Events
“What is happening across services?”
Health
“Are dependencies operating correctly?”
Same data, different filter. All four exist at both altitudes — tenant-wide for the Platform Admin, scoped to one app for the App Admin.

Settings

Cross-cutting configuration, kept separate from daily administration

Grouped into Account, Provisioning, Applications, and Data & Security — platform-level configuration that affects multiple areas at once.

Account — organization profile and account-level information.
Provisioning — how users sync with the platform, via SCIM, AD Sync or manual invites.
Applications — which AI applications are enabled for the organization.
Data & Security — residency, retention and encryption configuration.
Platform shapes the tenant, app shapes itself. An App Admin's settings apply only to their own application.

Same model, different scope

From user-level scope to platform-level scope.

I initially worked through administrative scope at the level of individual users, roles and permissions. As the architecture evolved, that same question became larger: which responsibilities belong to the platform, and which belong to the application?

User-level scope → platform-level scope

Same concept. Different scope.

Platform approves the catalog. App configures how it's used.

Platform sees the full bill. App sees its own consumption.

Same underlying data. Different filter.

Latest admin model

Two levels of control. One shared structure.

A Platform Admin who manages the tenant, and an App Admin who runs one application inside it — each with the same core jobs, at a different altitude.
