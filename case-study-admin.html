Designing Administration for an Enterprise AI Platform

Structuring organization, access, integrations, usage and platform operations into one manageable administration experience.

Background

As the platform grew,
administration became a product of its own.

An enterprise AI platform isn't only about building AI experiences. Someone also has to manage the organization behind them — users, permissions, workspaces, integrations, usage, security and system health.

The Administration experience needed to bring these responsibilities into a structure that could scale without becoming one large settings menu.

Today
Each team builds its own admin.

BAIC and every app invent separate admin patterns — different vocabulary, different layouts, different mental models. The fragmentation compounds with every new app.

Tomorrow

A shared vocabulary across platform and app. The platform surfaces tenant-wide concerns, each app surfaces its own — and a customer learns the structure once and reuses it everywhere.

Design principle
Group by the administrator's responsibility — not by the underlying system.

A flat list of settings pages mirrors how the system is built. Grouping by responsibility mirrors how an administrator actually thinks about their job — which is what the navigation needed to match.

Who this is for

Before the screens: two people share this experience, at two different altitudes.

Every section that follows belongs to one of two administrators. Designing for both meant giving each the right scope — not the same screen with fewer options switched off.

Platform Admin
Manages the platform.

Owns identity, security and tenant-wide governance. Connects SSO, defines the org hierarchy, and designates who administers each application.

App Admin
Runs an application.

Designated by the Platform Admin. Configures how one application uses what the platform has already approved and enabled — nothing more, nothing less.

Design principle
Set up once. Configure per app.

The platform connects identity, approves integrations and apps, and sets tenant-wide policy. Each app then configures how it uses what the platform has already enabled — credentials live once, behavior is per app. Two apps can share the same Salesforce connection and still do completely different things with it: one reading customer-support cases, the other reading sales-pipeline data, off the same credential.

The sections below follow this same split. Where a section exists at both altitudes, it keeps the same name and the same vocabulary — only the scope changes.

Organization

Understanding the organization before managing the system

For enterprise customers, administration can exist across organizational levels. The Organization area gives administrators a starting point for understanding the sub-organizations they can manage and moving into the relevant context.

Governance

Administration also means governing what AI is allowed to do.

As AI systems take actions, some may require human review. Governance sits within the organizational context rather than as a separate experience — the Human-in-the-Loop queue surfaces high-risk actions that require administrator approval or rejection.

Pending approvals
Every action waiting on a human decision, in one queue.
Risk level
Not every action carries the same stakes — risk is surfaced up front.
Agent responsible
Know which Agent is asking, not just what it's asking for.
Reason / context
The context behind the request, not just the request itself.
Approve / reject
A decision an administrator can make with confidence, in place.
Platform Admin only. Governance policy is set once, tenant-wide — apps don't maintain their own separate approval queues.

Integrations

Connecting the platform to the enterprise ecosystem

AI systems rarely operate independently. Administrators need visibility into the external systems the platform depends on. Connectors organizes integrations by operational state — In Use, Available, Requested, Catalog — and each active integration surfaces its health and the actions administrators are most likely to need.

Connectors manage integrations as products or services. API Tokens manage programmatic access to the platform itself — a related but distinct concern.

Credits & usage

Making AI consumption visible

AI introduces a new administrative concern: consumption. Administrators need to understand not only whether the system is working, but how platform capacity is being consumed — total inferences, daily burn, allocation, usage by skill, usage trend and model-level consumption, all in one place.

Both altitudes, different scope. Platform Admin sees the full account bill across every app; App Admin sees only this app's consumption and manages its own budget.
Design principle
Start with the health of the account — then let administrators investigate.

Total inferences and daily burn answer "is this normal?" first. Usage by skill and model-level detail are one level down, for administrators who need to know why.

Observability

From configuration to operational awareness

Audit Logs, Sign-ins, System Events and Health look similar at first glance, but they answer four different administrator questions.

Observability
Audit Logs
“What changed, and who did it?”
Sign-ins
“Who is accessing the platform?”
System Events
“What is happening across services?”
Health
“Are dependencies operating correctly?”
Same data, different filter. Audit logs, sign-ins, system events and health all exist at both altitudes — tenant-wide for the Platform Admin, scoped to one app for the App Admin.

Settings

Keeping cross-cutting configuration separate from daily administration

Settings contains platform-level configuration that affects multiple areas rather than everyday operational management — grouped into Account, Provisioning, Applications, and Data & Security.

Account — organization profile, workspaces and account-level information.
Provisioning — how users and organizational structure sync with the platform, via SCIM, AD Sync or manual invites. SCIM: automated user and group provisioning from an identity provider.
Applications — which AI applications are enabled and configured for the organization.
Data & Security — data residency, retention, encryption and compliance-related configuration.
Platform shapes the tenant, app shapes itself. Account, Provisioning and Data & Security apply tenant-wide; an App Admin's settings — credit limits, security overrides — apply only to their own application.
