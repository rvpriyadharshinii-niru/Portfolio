Designing beyond Figma

How I used Claude Code, our design system and GitHub to move from requirements to working product experiences.

While working on newer BAIS experiences such as AI Agents and Administration, our design process increasingly moved beyond static screens. Instead of designing the entire experience in Figma and handing it over, we started using AI-assisted coding as part of the design process itself.

Where it started

Claude wasn't the starting point.
The product problem was.

Before starting a new experience, we first structured the product and UX requirements. For larger projects, this included a tailored UX requirements document — a UXRD — describing the experience we were trying to create.

A UXRD could include things such as product context, users and personas, the jobs they need to accomplish, key journeys, product requirements, UX requirements, important states, constraints and expected behaviour.

Design system as context

The next challenge was consistency.

Generating an interface with AI is easy. Generating something that actually belongs inside an existing enterprise product is much harder.

We already had an established design system with reusable components documented in Storybook, connected to our codebase and GitHub workflow — so Claude could work with the components and patterns that already existed, instead of inventing new ones.

Building the experience

Then we started designing in the product itself.

Once the requirements and design-system context were available, I used Claude Code inside our development environment — tools like VS Code / Antigravity, with the project environment already set up — to start building the experience directly, rather than creating an isolated visual prototype.

I could describe the experience, build it, run it, interact with it, and immediately continue designing.

Iteration loop

Build → use → notice → change.

The biggest advantage wasn't simply generating screens faster. Once the experience was functional, I could actually use it — and that exposed problems that are sometimes difficult to notice in static screens.

Interaction behaviour Missing states Information hierarchy Navigation Responsive behaviour Component behaviour Longer end-to-end flows

Claude could quickly make many of those changes. But not every design problem was solved through prompting. Sometimes I went back into Figma. Sometimes I manually adjusted the design. Sometimes I changed the implementation directly. Sometimes Claude handled the iteration.

Figma's role

Code didn't replace Figma.

The workflow wasn't “Figma vs. Claude.” We used whichever surface helped us make the next design decision fastest. For certain explorations, Figma was still faster. For interaction-heavy experiences, Claude Code let us work directly with a functioning interface. For reviews, prototype screens could be brought back into Figma so PMs, designers and other stakeholders could review the experience in a familiar, collaborative environment.

Feedback loop

Then we connected feedback back into the build.

Once prototype screens were brought into Figma, the team could review them normally and leave comments. We created a workflow that allowed Claude to read the relevant Figma feedback — so feedback could move back into the implementation loop without manually translating every small comment into another long instruction.

“Automation shortened the feedback loop.
It didn't remove the designer from it.”

Working across GitHub

The prototype wasn't trapped on my machine.

We maintained the work through GitHub. Designers could work through branches, push their latest changes, and let another designer or collaborator pull the current version and continue from there — so the prototype behaved more like a shared product artifact than a disposable one.

Claude reduced the distance between an idea and something I could actually use. But deciding what to build, how the experience should behave, whether an AI-generated solution made sense, and when something needed manual design judgement still remained my responsibility.

AI didn't remove design from the process
It removed some of the distance between designing and building.
Understand Structure Design Build Use Review Iterate Share

Not a designer who makes Figma, hands it to engineering, and waits — but one who can understand, structure, design, build with AI, use, review, iterate and share. AI-generated output still needs human product and design judgement to become a real experience.
